# 分层职责边界对齐重构

针对本仓库（MetaData，依赖方向 Abstractions ← Providers ← Core ← Web）的目录与分层整理。核心原则：**先分析、确认粒度，再机械落地**，把"等价搬迁"与"业务语义改写"严格分开。

## 1. 分析（不动代码）

1. 列出目标目录全部文件，按**角色**归类每个类型，例如策略（XxxDialect/XxxInspector）、注册表（XxxRegistry）、DTO/样本、内部辅助类、接口契约。
2. 用 Grep 收集每个类型的**全部使用点**，确认三件事：
   - 跨模块引用方向是否合法（Core 不应依赖 Providers 的具体类，应只依赖 Abstractions 接口）；
   - 消费方引用的是接口还是具体实现；
   - 该类型是仅模块内部使用（可 internal）还是对外契约。
3. 与**仓库既有约定**对比：同类的其他类型如何放置（如三个 Registry 是否都有接口、是否都在 Registries 目录）。对齐既有约定优先于发明新抽象。
4. 诚实写出反方观点：文件数量少、一屏可览时不必过度拆分；单一实现且无扩展需求时按 YAGNI 可不抽接口。明确指出哪些是真实语义越界、哪些只是理论上的扩展点。

## 2. 确认粒度

目录移动会改变命名空间并产生连锁修改，必须先让用户确认。给出 2–3 个候选方案（推荐项放第一并标注），区分不同力度，例如：仅搬迁目录 / 搬迁 + 抽接口 / 维持现状。用户答复互相矛盾时，列出冲突点再追问一次，不要自行猜测。

## 3. 落地（按依赖顺序）

按"**契约定义处 → Providers 实现 → Core 消费方 → Web 宿主**"的顺序修改，让编译错误收敛在边界：

1. **命名空间跟随目录**：移动文件时同步改为 `项目名.文件夹名`（本仓库约定）。
2. **抽接口**：跨层被依赖的具体类，在 Abstractions 对应位置补接口（一类一文件，文件名即类型名）；业务 DTO 留在 Core，不进 Abstractions。
3. **更新 using**：所有引用方按新命名空间调整；不再需要的 using 一并删除。
4. **可访问性**：仅模块内部使用的实现细节下沉子目录并改 `internal sealed`；注意 internal 类型不得出现在 `public/protected` 签名上——遇到 CS0051 时，核查方法是否有外部/子类调用，没有就把方法收窄为 `private`。
5. **DI 注册**：具体类改为接口后，注册同步改为 `AddSingleton<IXxx, Xxx>()`。
6. **同步文档**：更新 `backend/ARCHITECTURE.md` 的模块图、命名空间职责表、目录树，不可遗漏。

## 4. 验证（全部通过才算完成）

1. `dotnet build MetaData.slnx`：目标 0 警告 0 错误。
2. `dotnet test MetaData.slnx --no-build`：全部测试通过。
3. Grep 复查旧类型名/旧命名空间残留，确认具体实现的引用已收敛在应有边界内。
4. 编译报错时先定位是否为漏 using 或可访问性问题，修复后重新构建，不跳过验证。

## 关键禁区

- 不做"为减类而减类"的激进压缩，不把面向扩展的策略/注册表内联掉。
- 不在一次提交里混入业务逻辑改写；本轮只做等价搬迁与契约对齐。
- 不新建 README/变更日志等非必要文件。
- 不主动扩大范围：只处理用户确认的目录，相邻目录的同类问题仅提示、不擅改。
